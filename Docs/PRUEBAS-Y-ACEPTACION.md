# Pruebas y criterios de aceptación

Esta matriz ayuda al equipo a revisar el acceso a Cenit, el registro de compras y la consulta académica. Para cada caso indica qué preparar, qué resultado esperar, qué pruebas existen y qué falta validar. Corresponde al MVP de Compras y académico; Personal y Bienes requieren sus propios casos cuando se definan sus requisitos.

Una prueba automática correcta demuestra el comportamiento que comprueba. La aceptación del contenido curricular, la precisión del OCR y la revisión con usuarios requieren además las fuentes y los criterios acordados con sus responsables.

## Cómo usar la matriz

1. Elegir el recorrido que se quiere revisar y preparar los datos ficticios indicados.
2. Comparar el resultado de Cenit con la columna «Resultado esperado».
3. Consultar la prueba enlazada y el registro de ejecuciones al final de este documento.
4. Registrar las observaciones y la aceptación en la tarea correspondiente o en el acta de revisión.

Los enlaces de las pruebas llevan al código que automatiza cada comprobación. Las referencias a historias permiten localizar sus criterios; no representan un cierre de esas historias.

## Ejecutar las pruebas

Las pruebas usan datos ficticios. Las de integración y navegador crean y eliminan sus propias bases y roles en PostgreSQL; por eso necesitan una instancia exclusiva de pruebas. No deben recibir una conexión administrativa de una base real.

| Comprobación | Comando | Qué revisa |
| --- | --- | --- |
| Reglas y formatos | `npm run test:unit` | Validaciones, contratos y transformaciones sin comprobar persistencia real |
| Integración PostgreSQL | `npm run test:integration` | API, permisos, transacciones, concurrencia y persistencia |
| Compilar la aplicación | `npm run build` | Contratos, API, cargador operativo y frontend que se usarán en los recorridos |
| Recorridos de navegador | `npm run test:e2e` | Aplicación compilada, login y recorridos administrativos/académicos |
| Sólo académico | `npm run test:e2e -- tests/e2e/academic.spec.ts` | Recorridos académicos existentes |
| Revisar el mockup de prerrequisitos | `npm run test:e2e -- tests/e2e/academic.spec.ts --grep 'fictici[oa]s' --output tmp/prerequisite-review/screenshots` | Seis estados y cadena ficticia, intención de hover, teclado, móvil y capturas fuera de Git |
| Persistencia y filtros de compras | `npm run test:integration -- tests/integration/purchases.test.ts tests/integration/purchases-consistency.test.ts` | Casos para revisión independiente de SCRUM-53 y SCRUM-58 sobre PostgreSQL |
| Catálogo | `npm run catalog:check` | Archivo del plan, fuentes/hashes, reglas interpretadas y pendientes, sin publicarlo |
| Tipos y estilo de código | `npm run typecheck` y `npm run lint` | Consistencia de tipos y reglas de código |

Antes de integración y navegador, ejecutar el build. Configurar `ACADEMIC_TEST_ADMIN_URL_FILE` con el archivo privado de conexión al PostgreSQL de pruebas y evitar una variable `DATABASE_URL` heredada de otro entorno. Los recorridos de navegador comparten puerto y archivos temporales: ejecutar un solo harness a la vez.

El ensayo real de OCR es optativo: requiere procesador y pesos disponibles, `OCR_URL` y `CAPTURE_RECEIPT_KEY_FILE` configurados en la terminal del harness, y una captura ficticia en `tmp/ocr-layout-v2/full.png`. La [guía local](../deploy/LOCAL.md#ejecutar-el-build-de-demostración-con-ocr) explica la preparación del procesador y las muestras. Se habilita con `CENIT_E2E_REAL_OCR=1`; el comando es `npm run test:e2e -- tests/e2e/capture.spec.ts --grep 'captura real:'`. Los restantes casos de captura usan respuestas controladas para comprobar la interfaz.

El recorrido `purchase-export.spec.ts` conserva el archivo ficticio comprobado en `tmp/purchase-export/compras-ficticias.xlsx`, fuera de Git. Permite revisar manualmente las tres hojas y su relación por ID después de ejecutar el harness.

Los ejemplos de contratos están separados en `packages/contracts/src`; el catálogo de prueba parte de `catalogs/academic` y las preparaciones ficticias viven en `db/seeds`. Los archivos de `tests/integration` y `tests/e2e` contienen la ejecución de los escenarios. Se reutilizan esas pruebas; no se mantienen copias separadas para esta matriz. La simulación académica queda fuera. La ampliación opcional de Sheets se verifica con un doble de su API y PostgreSQL; probar el conector real requiere configurar explícitamente una planilla dedicada con datos ficticios según la guía local. Las pruebas no escriben en el archivo del cliente.

Para revisar el mockup, comparar las capturas `prerrequisito-<estado>-<ancho>.png` de ambos roles y registrar la aprobación u observaciones en SCRUM-72. El recorrido abre cada ejemplo desde la malla con Enter, consulta información del plan con Tab/Enter, cierra con Escape y comprueba el retorno de foco y la ausencia de desbordamiento. La evidencia de navegador no sustituye una prueba en dispositivo físico ni la aprobación del diseño para SCRUM-75.
